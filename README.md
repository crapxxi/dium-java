# DIUM — Быстрый предзаказ еды в университетах

REST API бэкенд для платформы DIUM: студенты оформляют заказы в университетских кафе заранее, минуя очереди. Владелец заведения получает уведомление в WhatsApp, управляет статусом заказа и принимает оплату через Kaspi.

---

| Слой | Технология |
|---|---|

| Rate limiting | Bucket4j |
| Маппинг DTO | MapStruct |
| Документация API | SpringDoc OpenAPI (Swagger UI) |
| Контейнеризация | Docker (multi-stage build) |

### Слои приложения

**Controllers** — принимают HTTP-запросы, валидируют входные данные (`@Valid`), делегируют бизнес-логику сервисам. Разграничение доступа через `@PreAuthorize`.

**Services** — вся бизнес-логика. Каждый сервис отвечает за одну доменную область.

**Repositories** — доступ к БД через Spring Data JPA. `BaseRepository` расширяет `JpaRepository` и добавляет метод `findByIdOrThrow`.

**DTOs + Mappers** — запросы и ответы изолированы от моделей. MapStruct генерирует маппинг на этапе компиляции.

**AOP Aspect** — `MessageSenderAspect` перехватывает успешный возврат из `OrderService.createOrder` и асинхронно шлёт WhatsApp-уведомление владельцу заведения.

## Доменная модель

```
User (CLIENT / VENUE_OWNER / ADMIN)
 │
 ├── owns ──► Venue
 │             ├── has ──► Product
 │             │             └── has ──► ModifierGroup
 │             │                          └── has ──► Modifier
 │             └── receives ──► Order
 │                               └── contains ──► OrderItem
 │                                                  └── uses ──► Modifier[]
 └── places ──► Order
```

### Сущности

| Сущность | Описание |
|---|---|
| `User` | Пользователь системы; реализует `UserDetails`; идентифицируется по номеру телефона; хранит настройки 2FA |
| `Venue` | Заведение (кафе/буфет) в университете; у каждого заведения один `VENUE_OWNER` |
| `Product` | Позиция меню с категорией (`ProductCategory`), ценой и флагом наличия |
| `ModifierGroup` | Группа опций к продукту (например «Соусы», «Размер») |
| `Modifier` | Конкретная опция с дельтой цены (`priceDelta`) |
| `Order` | Заказ клиента; содержит список `OrderItem`, адрес доставки, статус, `pickupCode` |
| `OrderItem` | Строка заказа: продукт × количество × цена на момент покупки + выбранные модификаторы |
| `OtpCode` | Одноразовый код (активация / сброс пароля / вход с 2FA); хранится в Redis (при его недоступности — в Caffeine), ключ = телефон + назначение, TTL 5 мин |

## Жизненный цикл заказа

```
CLIENT создаёт заказ
        │
        ▼
    PENDING  ──── VENUE_OWNER отклоняет ──► CANCELLED
        │                                    (WhatsApp → CLIENT)
        │ VENUE_OWNER принимает
        ▼
   PREPARING  ◄─ WhatsApp уведомление → CLIENT ("Заказ готовится")
        │
        │ VENUE_OWNER готов выдать
        ▼
     READY    ◄─ WhatsApp уведомление → CLIENT ("Заказ готов, код: XXXX")
        │
        │ VENUE_OWNER завершает
        ▼
   COMPLETED
```

Генерация `pickupCode`: детерминированная формула `(id × 48271) % 9000 + 1000` — всегда 4-значное число.

## Доставка студентами

Покупатель сам выбирает, как получить заказ: самовывоз или доставка. Доставку выполняют сами студенты (роль `CLIENT`): каждый студент одновременно заказчик и курьер. Доставка стоит одинаково за весь заказ — `delivery.fee`, по умолчанию 100 ₸, сколько бы в заказе ни было товаров: столько платит клиент и столько же получает курьер (сумма фиксируется в доставке при её создании). Заказ с самовывозом в ленту курьеров не попадает.

```
Заведение принимает заказ с адресом (PENDING → PREPARING)
        │
        ▼
 SEARCHING_COURIER ── заказ в ленте курьеров (кроме самого заказчика)
        │  студент нажимает «Взять заказ» и получает код курьера
        ▼
     ASSIGNED ───── курьер отказался / админ снял ──► снова SEARCHING_COURIER
        │  заказ READY, заведение вводит код курьера
        ▼
    PICKED_UP ───── клиенту в WhatsApp уходит его код
        │  курьер вводит код, который назвал клиент
        ▼
    DELIVERED ───── заказ → COMPLETED, курьеру засчитана оплата

любой незавершённый статус ── админ / отмена заказа ──► CANCELLED
```

Пока доставка не завершена, заведение не может само отметить заказ выданным: заказ завершается только кодом клиента.

### Три вкладки

| Кто | Где во фронтенде | Что делает |
|---|---|---|
| Студент | «Доставка» (`/delivery`) | Свободные заказы → взять; «Мои доставки» — код для заведения, ввод кода клиента, заработок; «Мне везут» — курьер и свой код |
| Владелец заведения | «Кухня» → вкладка «Доставки» | Кто везёт заказ, передача курьеру по его коду, отметка «доставлено» |
| Администратор | «Доставки» (`/admin/deliveries`) | Все доставки и проблемы; снять курьера, отменить, завершить без кода, разблокировать коды, закрыть проблему |

### Как гарантируется, что заказ действительно доставлен

1. **Два одноразовых кода.** Код курьера видит только назначенный курьер; заведение вводит его при передаче — заказ получает именно тот студент, который его взял. Код клиента видит только клиент; курьер вводит его у двери — без него доставка не завершится и оплата не засчитается.
2. **Коды не лежат в БД открыто.** Случайные 4 цифры (`SecureRandom`), хранятся зашифрованными AES-256-GCM (тот же ключ, что у TOTP), сравниваются за постоянное время. Заведение и администратор кодов не видят.
3. **Лимит попыток.** После 5 неверных вводов код блокируется (дальше не принимается даже верный), автоматически создаётся проблема `CODE_LOCKED`. Разблокирует администратор — заблокированный код при этом заменяется новым. Счётчик сохраняется даже при ошибке запроса (`@Transactional(noRollbackFor = …)`).
4. **Гонки.** `@Version` на доставке: если два курьера одновременно нажали «Взять», второй получает `409`. Лимит активных доставок на курьера (`max-active-per-courier`, по умолчанию 2) защищён блокировкой строки курьера.
5. **Права.** Курьер — только `CLIENT` и не по своему заказу; передавать курьеру может только владелец этого заведения (`@CheckOwnership(DELIVERY)`); действия администратора — только `ADMIN` и всегда с причиной, которая сохраняется в доставке.
6. **Приватность.** Телефоны клиента и курьера видны друг другу только пока доставка в работе; в ленте свободных заказов данных клиента нет.
7. **Журнал.** Триггер пишет каждую смену статуса доставки в `delivery_status_history` (вместе с курьером), а БД отклоняет недопустимые переходы — даже при ручной правке.

### Проблемы

Клиент, курьер и заведение могут сообщить о проблеме по своей доставке (`NOT_DELIVERED`, `COURIER_NOT_ARRIVED`, `CUSTOMER_UNREACHABLE`, `CUSTOMER_REFUSES_CODE`, `DAMAGED_OR_WRONG`, `OTHER`); `CODE_LOCKED` создаёт система. Администратор видит открытые проблемы, переходит к доставке и закрывает проблему с описанием решения.

### Баллы

Курьер получает за доставку баллы, а не деньги: 1 балл за 1 ₸ платы за доставку (100 баллов). Баллами можно оплатить заказ целиком в любом заведении, но цена в баллах выше на наценку (`WALLET_POINTS_MARKUP_PERCENT`, по умолчанию 20%): 1000 ₸ еды = 1200 баллов. Наценка остаётся платформе, поэтому гонять заказы «по кругу» невыгодно.

- **Журнал.** Баланс (`wallets`) меняется только вместе с записью в `wallet_transactions`. Журнал только дописывается: `UPDATE` и `DELETE` запрещены триггером, баланс не уходит в минус (`CHECK`).
- **Один раз.** У каждой автоматической операции есть ключ (`delivery-earning:{id}`, `order-payment:{id}`, `order-refund:{id}`, `delivery-refund:{id}`): повтор ничего не начислит и не спишет второй раз.
- **Без перерасхода.** Кошелёк блокируется на время операции (`SELECT … FOR UPDATE`): два одновременных заказа не потратят одни и те же баллы. Не хватает баллов — заказ не создаётся.
- **Когда начисляется.** Курьеру — только после кода клиента или завершения администратором. Покупателю возвращаются все баллы, если заведение отменило заказ или не приняло его за 5 минут, и баллы за доставку, если доставку отменили.
- **Нет вывода и переводов.** Баллы нельзя обменять на деньги или передать другому пользователю. Администратор может начислить или списать баллы вручную с причиной, но не себе.
- **Сверка с заведениями** (`GET /api/v1/admin/settlements`). По Kaspi-доставкам заведение получило 100 ₸ за доставку, а курьер — баллы, значит, заведение должно платформе. Заказ за баллы заведение отдало без денег — платформа должна ему стоимость еды в тенге.

## Аутентификация

Все защищённые эндпоинты требуют заголовок `Authorization: Bearer <JWT>`.

```
Регистрация → OTP в WhatsApp → Активация → JWT
Вход: телефон + пароль → (если включена 2FA) временный токен → код → JWT
```

### Регистрация и подтверждение телефона

1. `POST /api/v1/auth/register` — создаёт пользователя (`isConfirmed = false`) и отправляет 6-значный код в WhatsApp.
   Если код отправить не удалось, пользователь **не создаётся**, клиент получает `502` с понятным сообщением.
2. `POST /api/v1/auth/activate?phone=&code=` — подтверждает телефон, возвращает JWT.
3. `POST /api/v1/auth/resend-code?phone=` — повторная отправка кода (не чаще раза в 60 секунд).
4. `POST /api/v1/auth/forgot-password?phone=` → `POST /api/v1/auth/reset-password` — сброс пароля по коду.

Аккаунт заблокирован (`isAccountNonLocked = false`), пока `isConfirmed = false`.

**Номера телефонов** нормализуются на бэкенде к виду `7XXXXXXXXXX`: принимаются `+7 (707) 123-45-67`,
`8 707 123 45 67`, `77071234567`, `7071234567`. Некорректный номер → `422`.

### Одноразовые коды (OTP)

| Свойство | Значение |
|---|---|
| Длина / срок жизни | 6 цифр / 5 минут |
| Попытки ввода | 5, затем код аннулируется |
| Повторная отправка | не чаще 1 раза в 60 секунд (`429` + `Retry-After`) |
| Назначения | `ACTIVATION`, `PASSWORD_RESET`, `LOGIN_2FA` — ключ кэша = телефон + назначение, код одного назначения не подходит для другого |
| Сравнение | за постоянное время (`MessageDigest.isEqual`) |

Отправка считается успешной только при HTTP 2xx **и** наличии `idMessage` в ответе Green API.

#### Хранилище кодов: Redis + Caffeine

Коды хранятся в Redis (hash `dium:otp:<телефон>:<назначение>` с TTL = сроку жизни кода; запись и счётчик попыток
меняются атомарно Lua-скриптами), поэтому они общие для всех экземпляров приложения и переживают перезапуск.

Каждое обращение к Redis идёт через circuit breaker (Resilience4j, `ResilientOtpRepository`):

| Состояние | Что происходит |
|---|---|
| `CLOSED` | Коды читаются и пишутся в Redis. Отдельный упавший запрос сразу выполняется в Caffeine |
| `OPEN` | Из последних 20 обращений упало ≥ 50% — 30 секунд к Redis не обращаемся вовсе, коды живут в Caffeine (запросы не ждут таймаутов) |
| `HALF_OPEN` | 3 пробных запроса к Redis: успешны — возврат в `CLOSED`, нет — снова `OPEN` |

При переключениях коды не теряются и не используются повторно: если кода нет в Redis, он ищется в Caffeine
(коды, выданные во время сбоя, продолжают работать); код, который не удалось удалить из Redis после использования,
игнорируется, пока не будет удалён. Код, выданный в Redis до сбоя, во время сбоя недоступен — пользователь
запрашивает новый. Во время сбоя коды видны только тому экземпляру приложения, который их выдал.

Пороги настраиваются в `otp.storage.circuit-breaker.*`, подключение — `spring.data.redis.*` (таймауты 500 мс).
`OTP_REDIS_ENABLED=false` отключает Redis полностью (только Caffeine, как раньше).

### Двухфакторная аутентификация (2FA)

Способы: **WhatsApp** (одноразовый код) и **TOTP** (Google Authenticator и совместимые приложения).
Дополнительно выдаются 10 одноразовых **резервных кодов**.

Вход при включённой 2FA:

1. `POST /api/v1/auth/login` — пароль верный, но JWT **не выдаётся**. Ответ:
   ```json
   { "token": null, "twoFactorRequired": true, "tempToken": "...", "twoFactorMethod": "TOTP",
     "availableMethods": ["TOTP", "WHATSAPP"], "codeSent": null, "backupCodesAvailable": true }
   ```
   `tempToken` — JWT с пометкой `2fa_pending`, живёт 5 минут. `JwtAuthenticationFilter` отклоняет его (`401`)
   на всех эндпоинтах, кроме `/api/v1/auth/2fa/verify`.
2. `POST /api/v1/auth/2fa/verify` — `{ "tempToken", "code", "method": "WHATSAPP" | "TOTP" | "BACKUP_CODE" }`.
   Только после верного кода возвращается настоящий JWT.

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/api/v1/auth/2fa/verify` | tempToken | Завершить вход кодом |
| POST | `/api/v1/auth/2fa/verify/send-code` | tempToken | Отправить (повторно) WhatsApp-код для входа |
| GET | `/api/v1/auth/2fa/status` | JWT | Включена ли 2FA, способ, обязательность, остаток резервных кодов |
| POST | `/api/v1/auth/2fa/setup` | JWT | Начать подключение: TOTP → секрет + `otpauth://` URI + QR; WhatsApp → проверочный код |
| POST | `/api/v1/auth/2fa/enable` | JWT | Подтвердить кодом и включить; возвращает резервные коды (один раз) |
| POST | `/api/v1/auth/2fa/send-code` | JWT | WhatsApp-код текущему пользователю (для отключения) |
| POST | `/api/v1/auth/2fa/disable` | JWT | Отключить: нужны пароль и код |
| POST | `/api/v1/auth/2fa/backup-codes` | JWT | Перевыпустить 10 резервных кодов (нужен пароль) |

Хранение: TOTP-секрет шифруется AES-256-GCM (ключ `TWO_FACTOR_ENCRYPTION_KEY`), резервные коды — только BCrypt-хэши.
После 5 неверных кодов подряд проверка блокируется на 5 минут.

**Обязательная 2FA для `ADMIN` и `VENUE_OWNER`** — флаг `TWO_FACTOR_REQUIRED_FOR_STAFF` (по умолчанию `true`).
Если такой пользователь сам 2FA не настраивал, при входе код приходит в WhatsApp; подключив TOTP, он входит по коду из приложения.

| Роль | Возможности |
|---|---|
| `CLIENT` | Регистрация, просмотр меню/заведений, создание и просмотр своих заказов; доставка чужих заказов курьером |

## Rate Limiting (Bucket4j + Caffeine)

`RateLimitFilter` ограничивает `POST`-запросы на каждую пару «IP + эндпоинт»:

| Эндпоинты | Лимит |
|---|---|
| `/api/v1/auth/register`, `/login`, `/activate`, `/resend-code`, `/forgot-password`, `/reset-password` | 10 запросов / минута |
| `/api/v1/auth/2fa/**` | 10 запросов / минута |

Лимит настраивается (`RATE_LIMIT_CAPACITY`, `RATE_LIMIT_ENABLED`). При превышении: `HTTP 429 Too Many Requests` + `Retry-After`.
Перебор конкретного кода дополнительно ограничен самим OTP (5 попыток) и блокировкой 2FA.

## Переменные окружения

| Переменная | Описание | Dev-дефолт |
|---|---|---|
| `JWT_KEY` | Секрет для подписи JWT (Base64, ≥ 32 байт). **В prod обязателен** | dev-ключ |
| `WHATSAPP_API_URL` | Хост Green API без пути (`apiUrl` из личного кабинета). **В prod обязателен** | `https://api.green-api.com` |
| `WHATSAPP_INSTANCE_ID` | ID инстанса Green API. **В prod обязателен** | — |
| `WHATSAPP_API_TOKEN` | Токен Green API. **В prod обязателен** | — |
| `TWO_FACTOR_ENCRYPTION_KEY` | Ключ AES-256 для TOTP-секретов: Base64 от 32 байт (`openssl rand -base64 32`). **В prod обязателен**; при смене ключа настроенные TOTP перестают работать | dev-ключ |
| `TWO_FACTOR_REQUIRED_FOR_STAFF` | Обязательная 2FA для `ADMIN` и `VENUE_OWNER` | `true` |
| `OTP_REDIS_ENABLED` | Хранить OTP-коды в Redis (при сбое — Caffeine); `false` — только Caffeine | `true` |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` / `REDIS_SSL` | Подключение к Redis | `localhost` / `6379` / — / `false` |
| `RATE_LIMIT_ENABLED` / `RATE_LIMIT_CAPACITY` | Лимит запросов к auth-эндпоинтам (запросов в минуту с IP) | `true` / `10` |
| `DELIVERY_FEE` | Цена доставки за заказ (платит клиент, получает курьер), ₸ | `100` |
| `WALLET_POINTS_MARKUP_PERCENT` | На сколько процентов цена в баллах выше цены в тенге | `20` |
| `CLOUDINARY_CLOUD_NAME` | Cloudinary cloud name | `temp` |
| `CLOUDINARY_API_KEY` | Cloudinary API key | `12345` |
| `CLOUDINARY_API_SECRET` | Cloudinary API secret | `secret` |
| `SPRING_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD` | PostgreSQL (prod-профиль) | — |
| `PORT` | Порт сервера | `8080` |

## Запуск

### Локально (dev-профиль)

```bash
cp .env.example .env   # и заполните значения
./mvnw spring-boot:run  # Windows: mvnw.cmd spring-boot:run
```

### Docker

```bash
docker build -t dium-backend .
docker run -p 8080:8080 \
  -e JWT_KEY=... \
  -e TWO_FACTOR_ENCRYPTION_KEY=... \
  -e WHATSAPP_API_URL=... \
  -e WHATSAPP_INSTANCE_ID=... \
  -e WHATSAPP_API_TOKEN=... \
  -e CLOUDINARY_CLOUD_NAME=... \
  -e CLOUDINARY_API_KEY=... \
  -e CLOUDINARY_API_SECRET=... \n  -e REDIS_HOST=... \
  dium-backend
```

Prod-профиль активируется автоматически через `ENTRYPOINT` в Dockerfile.

### Тесты

```bash
./mvnw test
```

Обычный прогон обходится без Redis (коды в Caffeine; переключение Redis → Caffeine проверяется на «падающем» Redis).
Тесты на настоящем Redis включаются переменной `REDIS_TEST_HOST`:

```bash
docker run -d --name redis -p 6379:6379 redis:7-alpine
REDIS_TEST_HOST=localhost ./mvnw test
```
